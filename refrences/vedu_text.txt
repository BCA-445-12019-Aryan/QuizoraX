Platform) is a full-stack, cloud-native virtual classroom platform built to deliver live, interactive online education using WebRTC technology. The name VEDU is inspired by the Sanskrit word Vidya (विद्या), meaning knowledge or learning. VEDU provides educators, students, and administrators with dedicated, role-based portals that manage the complete lifecycle of a digital classroom — from account registration and class scheduling, through live video sessions with interactive whiteboard functionality and real-time recording, to post-session video playback from cloud storage.The platform is architected as a collection of containerized microservices orchestrated by Docker Compose and exposed securely to the internet through Caddy reverse proxy, which automates HTTPS certificate management via Let's Encrypt. The backend is implemented in Java 17 using Spring Boot 3.1.2, providing RESTful APIs consumed by a pure vanilla HTML/CSS/JavaScript frontend.Real-time media transport is handled by LiveKit — an open-source WebRTC Selective Forwarding Unit (SFU) — and session recordings are produced by LiveKit Egress, stored in a MinIO S3-compatible object store, and served over a Caddy-proxied storage path. VEDU is deployed on a Microsoft Azure virtual machine running Ubuntu 22.04 LTS, accessible at https://vedulive.net2coder.in.1.2 Background and ContextThe COVID-19 pandemic permanently transformed educational delivery worldwide. Where physical classrooms once served as the default medium for instruction, institutions discovered that digital alternatives could serve learners effectively — sometimes even more flexibly. However, the landscape of available video conferencing solutions remains dominated by large, expensive, privacy-invasive commercial platforms such as Zoom, Microsoft Teams, and Google Meet, which suffer from several significant drawbacks:Vendor Lock-in: User data, recordings, and accounts are owned and controlled by the vendor, creating dependency on third-party terms and pricing.No Educator-Specific Workflow: Features like per-batch scheduling, course-organized recordings, and roster-aware email notifications are absent or require additional paid third-party tools.Limited Customization: Institutions cannot adapt the user interface to their brand or modify the user experience to match their pedagogical approach.Privacy Concerns: Video streams and recordings are routed through vendor servers in potentially unknown jurisdictions, raising data sovereignty issues.Cost Barriers: Subscription fees for premium features are prohibitive for smaller educational institutions.VEDU was designed to address all of these concerns simultaneously. By building on open-source infrastructure — LiveKit, MinIO, Redis, and PostgreSQL — institutions retain full control over their educational data. By deploying on their own cloud virtual machine, they ensure data sovereignty.1.3 Motivation for VEDUThe motivation for developing VEDU is threefold:Technical Motivation: To create a production-grade demonstration of WebRTC SFU architecture integrated with a modern Spring Boot REST API, JWT-based authentication, and S3-compatible object storage — combining multiple cutting-edge technologies into a cohesive educational platform.Educational Motivation: To provide institutions with a self-hostable, open-architecture alternative to costly proprietary platforms, giving educators control over their teaching environment, data, and student interactions.Operational Motivation: To automate common instructor workflows — scheduling, student email notification, recording management, and session lifecycle management — that previously required manual effort or paid third-party integrations.1.4 Scope of the SystemVEDU encompasses the following functional scope in its current Version 3.1.2 runs on Jakarta EE 10, providing the definitive modern Java enterprise API. Spring Boot's hallmark is its auto-configuration mechanism, which inspects the JARs on the classpath and automatically configures appropriate Spring beans — eliminating hundreds of lines of XML configuration that legacy Spring applications required.Key Spring Boot features used in VEDU include:@SpringBootApplication: Composite annotation enabling auto-configuration, component scanning, and configuration class processing.@EnableAsync: Enables Spring's asynchronous method execution infrastructure, used for non-blocking email dispatch.@EnableScheduling: Activates Spring's built-in task scheduler for the automated session status update service.Spring Data JPA: Repository abstraction providing zero-SQL database access for CRUD operations and query derivation.Embedded Tomcat: Spring Boot embeds a Tomcat servlet container, eliminating the need for external application server deployment.Spring Boot Actuator: Provides production-ready health check endpoints used by the Docker container healthcheck.CHAPTER 4: ADVANTAGES OF JAVA & SPRING BOOT4.1 Advantages of JavaPlatform Independence: Java bytecode runs on any JVM regardless of the underlying operating system or hardware architecture. VEDU's backend runs identically on the developer's Windows machine (via Docker) and the Azure Ubuntu production VM.Object-Oriented Design: Java's class-based OOP enables clean separation of concerns through Models, Repositories, Services, and Controllers — following the layered architecture pattern that makes VEDU maintainable and extensible.Strong Typing & Compile-Time Safety: Java's static type system catches type errors at compile time, preventing entire classes of runtime bugs. Tools like Lombok reduce boilerplate while preserving type safety.Rich Ecosystem: Maven Central hosts over 500,000 Java libraries. VEDU leverages Spring Boot, LiveKit Java SDK, MinIO Java SDK, JJWT, and Lombok — all available as simple Maven dependencies.Enterprise-Grade Performance: The Java HotSpot JIT compiler optimizes frequently executed code paths at runtime, making Spring Boot REST APIs highly performant under concurrent load.Excellent Concurrency Support: Java's threading model, combined with Spring's @Async and CompletableFuture, enables VEDU to handle concurrent API requests while dispatching emails in background threads.Long-Term Support: Java 17 LTS receives security and bug-fix updates until 2029, making it suitable for production educational systems with long maintenance windows.Community and Documentation: Java has one of the largest programming communities globally, ensuring rapid resolution of technical challenges and extensive reference material.4.2 Advantages of Spring BootAuto-Configuration Reduces Boilerplate: Spring Boot auto-configures Tomcat, Hibernate, SMTP, and other infrastructure based on classpath inspection — requiring zero XML configuration files in VEDU.Embedded Server Simplifies Deployment: Spring Boot's embedded Tomcat means the application is a self-contained JAR artifact. The Docker ENTRYPOINT is simply java -jar app.jar.Convention Over Configuration: Spring Boot provides sensible defaults for all configuration, allowing developers to focus on business logic rather than infrastructure plumbing.Production-Ready from Day One: Spring Actuator provides /actuator/health, /actuator/info, and other endpoints that integrate seamlessly with Docker healthchecks and monitoring systems.Spring Data JPA: Repository interfaces reduce data access code to interface declarations. VEDU's Student_repo, Teacher_repo, Schedules_repo, and RecordingRepository require zero SQL.Scheduling and Async: @Scheduled and @Async annotations enable background task scheduling and asynchronous execution without requiring a separate job scheduler service.RestTemplate and HTTP Integration: Spring's RestTemplate simplifies HTTP calls to external services like Supabase Auth and PostgREST, handling serialization, headers, and error responses.Excellent Testing Support: Spring Boot Test provides @SpringBootTest for integration tests and spring-security-test for security testing — beneficial for future automated test suites.Active Community and Regular Releases: Spring Boot releases regular patch versions with security fixes and new feature support, ensuring VEDU's dependencies remain current.4.3 Why LiveKit for WebRTC?LiveKit is an open-source, production-grade WebRTC Selective Forwarding Unit built in Go. Unlike Jitsi (complex configuration) or OpenVidu (uses Kurento/mediasoup), LiveKit was designed from the ground up for developer ergonomics. Its Java server SDK (io.livekit:livekit-server:0.12.1) allows token generation, room management, and egress control from within Spring Boot code. Its JavaScript client SDK provides a type-safe, event-driven API for browser-side WebRTC.In LiveKit's SFU model, each participant's browser maintains only ONE WebRTC connection to the LiveKit server. The SFU receives each participant's encoded bitstream and forwards it (without decoding) to all subscribed participants. This scales far better than peer-to-peer mesh (N×N connections) or an MCU (server-side decoding/re-encoding) approach, making it suitable for educational classrooms with multiple concurrent participants.CHAPTER 5: TOOLS AND PLATFORMS USED5.1 Development ToolsToolVersionPurposeIntelliJ IDEA2024.xPrimary Java IDE with Spring Boot supportApache While mass-market video conferencing platforms (Zoom, Teams, Google Meet) deliver basic audio/video, they fundamentally fail educators in several important ways:7.1 Core Problems AddressedProblem 1 — Data Sovereignty and Vendor Lock-in: When an institution uses Zoom or Teams to record lectures, those recordings are stored on vendor servers. The institution has no direct access to storage infrastructure, no ability to customize retention policies, and no guarantee of data jurisdiction. If the vendor changes pricing or discontinues a feature, the institution has no alternative without migrating all historical data.Problem 2 — Lack of Educator-Specific Workflow Automation: Teachers using general-purpose video conferencing tools must manually notify students about class schedules via separate messaging apps, manually track which students attended, and manually distribute recording links. There is no integrated workflow that connects scheduling, notification, live session, and recording into a unified system.Problem 3 — Absence of Course/Batch Filtering: General platforms treat all meetings as equal. Educational institutions need hierarchical organization — by course, by batch, by year — so students automatically see only the classes relevant to their enrollment. This filtering does not exist in Zoom or Teams without complex manual room management.Problem 4 — Recording Accessibility and Management: Recordings made on commercial platforms are accessible only through those platforms' web interfaces. Institutions cannot serve recordings through their own domain, cannot integrate playback into a student portal, and cannot delete recordings autonomously without platform-imposed retention periods.Problem 5 — Cost Barriers for Smaller Institutions: Commercial platforms charge per-host per-month licensing fees that are prohibitive for rural or resource-constrained educational institutions. A self-hosted, open-source alternative would eliminate licensing costs entirely, requiring only the cost of a basic cloud virtual machine.7.2 The VEDU Solution StatementVEDU solves all five problems simultaneously:Self-hosted on institution-controlled cloud VM — data never leaves the institution's infrastructure.Integrated scheduling-notification-session-recording workflow  a single system handles all educator tasks.Course/batch-based schedule filtering — students see only their relevant classes.Recordings stored in institution-controlled MinIO, served via institution's own domain.Zero licensing cost — all software dependencies are open-source.CHAPTER 8: REQUIREMENT SPECIFICATIONS8.1 Functional RequirementsThe following functional requirements define what The following needs were identified through stakeholder analysis involving students, teachers, and educational administrators:Need 1 — Affordable Real-Time Video Classroom: Institutions need a robust, real-time video conferencing solution that does not impose per-user licensing fees. Commercial platforms charge $14–$20 per host per month, creating significant cost barriers for institutions with large faculty counts.Need 2 — Integrated Scheduling with Batch Filtering: Current tools require teachers to use separate apps for scheduling (Google Calendar), notification (WhatsApp/Email), and sessions (Zoom). A single integrated system that handles all three — with automatic student filtering by batch/course — is essential.Need 3 — Self-Hosted Recordings with Instant Access: Teachers need recordings to be immediately available to students after a session ends, accessible within the same platform where they view the schedule. External recording storage (YouTube, Google Drive) creates friction and privacy concerns.Need 4 — Interactive Teaching Tools: A digital whiteboard that is captured in the session recording is a critical requirement for technical and mathematical content delivery. Software-based drawings visible in the recording preserve the full teaching value of the session.Need 5 — Administrative Oversight: Institutional administrators need real-time visibility into which classes are active, how many students are attending, and the ability to intervene (end a room, delete inappropriate content) without requiring LiveKit server access.10.2 Current System AnalysisThe existing system (pre-VEDU) in most educational institutions in India uses the following fragmented toolset:FunctionCurrent Tool UsedProblemLive Video SessionsZoom / Google Meet / JitsiNo institutional control, vendor dependency, per-user feesClass SchedulingWhatsApp groups / ManualNo automated notification, no batch filteringStudent NotificationWhatsApp / SMS / Email manuallyNo automation, error-prone, time-consumingRecording StorageZoom Cloud / Google DriveVendor-controlled, limited access customizationRecording AccessShared Google Drive linksSecurity concerns, difficult to organize by courseAdmin MonitoringNone / Manual attendanceNo real-time visibility into live sessionsAuthenticationNone / Separate LMS loginNo unified identity management10.3 Proposed System — VEDUVEDU replaces the fragmented toolset with a single, integrated platform. In contrast to peer-to-peer (P2P) WebRTC where every participant connects to every other participant (N×N connections), the SFU model requires only one connection per participant — to the SFU server. The SFU receives each participant's encoded video/audio bitstream and intelligently forwards it to subscribed participants WITHOUT decoding and re-encoding (unlike MCU).ICE candidate exchange (NAT traversal) occurs via the WebSocket signalling channel at /rtc. For participants behind NAT, LiveKit acts as a STUN server on UDP port 3478. If UDP is blocked by corporate firewalls, LiveKit falls back to TCP WebRTC on port 7881.12.5 Authentication FlowStep 1 — User submits email/password to POST /api/auth/login.Step 2 — Spring Boot forwards credentials to Supabase Auth: POST /auth/v1/token?grant_type=password.Step 3 — Supabase returns a signed JWT (access_token), refresh_token, and user identity (UUID, email).Step4 — Spring Boot queries Supabase PostgREST: GET /rest/v1/profiles?id=eq.{userId}&select=user_type to retrieve the user's role.Step 5 — Spring Boot returns {access_token, role} to the browser.Step 6 — Browser stores the JWT in localStorage.vedu_token and redirects to the role-specific dashboard.Step 7 — All subsequent API calls include Authorization: Bearer {JWT} in the request header.Step 8 — Spring Boot's TokenService.extractUserIdFromToken() decodes the JWT payload (Base64URL) and extracts the sub (UUID) claim for business logic.12.6 Recording Pipeline ArchitectureThe recording pipeline involves a two-phase database write pattern that ensures recording integrity even across backend restarts:Phase 1 — Recording Start:Teacher clicks 'Start Recording' → POST /api/meetings/recording/start.Backend validates JWT and checks role = 'teacher'.Backend calls EgressServiceClient.startRoomCompositeEgress(roomName, S3Config, 'speaker').LiveKit Egress spawns a headless Chromium browser that renders the room URL.Backend saves a pending Recording row with egressId, teacherId, roomName, and fileUrl = '' (empty string).Backend returns {egressId, status: 'recording'} to the teacher.Phase 2 — Recording Stop & Completion:Teacher clicks 'Stop Recording' → POST /api/meetings/recording/stop.Backend queries RecordingRepository.findTopByRoomNameAndFileUrlOrderByCreatedAtDesc(roomName, '') to find the active recording.Backend calls EgressServiceClient.stopEgress(egressId).LiveKit server fires an egress_ended webhook to: POST /api/meetings/livekit/webhook.Backend extracts the file location from the webhook payload (internal MinIO URL).Backend converts the internal URL to a public URL: https://vedulive.net2coder.in/storage/recordings/{filename}.mp4.Backend updates the Recording row: SET fileUrl = publicUrl WHERE egressId = egressId.Recording is now available in student and teacher recording portals.CHAPTER 13: DATA FLOW DIAGRAMS (DFD)13.1 Level 0 DFD — Context DiagramThe Level 0 DFD (Context Diagram) shows VEDU as a single process interacting with four external It is decorated with three essential class-level annotations that activate the complete Spring infrastructure:@SpringBootApplication — Composite meta-annotation combining @Configuration (marks the class as a Spring config source), @EnableAutoConfiguration (activates Spring Boot auto-configuration engine), and @ComponentScan (scans all sub-packages for @Component, @Service, @Repository, @Controller stereotypes).@EnableAsync — Activates Spring's asynchronous method execution infrastructure. Methods annotated with @Async (specifically EmailService.sendClassNotification()) run in a separate thread pool, allowing the HTTP response to be returned to the caller immediately while email dispatch continues in the background.@EnableScheduling — Enables Spring's built-in task scheduler. The ScheduleStatusService.autoComplete() method annotated with @Scheduled(fixedDelay = 30 * 60 * 1000) runs every 30 minutes automatically.16.2 JPA Entity ModelsVEDU uses four JPA entities, each annotated with @Entity and @Table for Hibernate persistence mapping. Lombok's @Data annotation eliminates boilerplate getter/setter/toString/equals methods at compile time.Student.java: Maps to the student table. The id field uses UUID type matching the Supabase Auth user UUID, annotated with @Column(updatable = false) to prevent primary key modification. Course values are normalized to UPPERCASE by StudentService before persistence.Teacher.java: Maps to the teacher table. The description and email fields use @Column(columnDefinition = "Text") to override Hibernate's default VARCHAR(255) DDL with PostgreSQL's unbounded TEXT type.Schedules.java: Maps to the Schedules table. Uses @GeneratedValue(strategy = GenerationType.IDENTITY) for auto-increment primary key. The status field defaults to 'UPCOMING'. The topicName field doubles as the LiveKit room identifier.Recording.java: Maps to class_recordings. Uses @CreationTimestamp for automatic created_at timestamp assignment. The egress_id column has @Column(unique = true) for idempotent webhook processing.16.3 Repository LayerSpring Data JPA repositories provide zero-SQL database access through interface declarations. Each interface extends JpaRepository<Entity, IdType>, inheriting full CRUD operations.Student_repo: Key method findByCourseIgnoreCaseAndStudentClassIgnoreCase() generates a JPQL query with UPPER() case-folding on both course and class predicates, used for email notification recipient lookup.Schedules_repo: Contains findByTeacheridOrderByTopicTimeAscAllIgnoreCase() for teacher's own schedule list, findByTopicCourseAndTopicClassOrderByTopicTimeAscAllIgnoreCase() for student schedule view, and a custom @Modifying @Query for the auto-complete batch UPDATE.RecordingRepository: Contains findByEgressId() for webhook processing, findTopByRoomNameAndFileUrlOrderByCreatedAtDesc() for active recording detection, and custom @Query methods using fileUrl <> '' to filter completed recordings.16.4 Service LayerSupabaseAuthService.java — Supabase Integration Gateway:signupUser(): POSTs to /auth/v1/signup with anonKey header. Replace the current Base64URL-decode-only approach with full JJWT signature verification using the SUPABASE_JWT_SECRET. This eliminates the entire class of forged-JWT user impersonation attacks.Enhancement 2 — Admin Endpoint Authentication (Security Priority)Add JWT-based authentication middleware to all /api/admin/* endpoints. Implement Spring Security with a JWT filter chain and @PreAuthorize('hasRole(ADMIN)') annotations on admin controller methods.Enhancement 3 — Presigned URL Recording Access (Security)Replace anonymous download MinIO bucket policy with time-limited presigned URLs generated per-request by the backend. This binds recording access to authenticated users and prevents URL guessing attacks.Enhancement 4 — HLS/DASH Adaptive StreamingPost-process MP4 recordings through FFmpeg into HLS (HTTP Live Streaming) segments for adaptive bitrate playback. Students on slow connections receive lower-bitrate segments; fast connections get HD quality. MinIO can serve the .m3u8 playlists and .ts segments directly.Enhancement 5 — Persistent In-Room ChatImplement WebSocket-based chat using Spring WebSocket (STOMP) or LiveKit's DataChannel API. Persist messages to PostgreSQL with session association for post-session review.Enhancement 6 — Real-Time Collaborative Whiteboard SyncSynchronize whiteboard state across all participants in real time using LiveKit DataChannel or a WebSocket endpoint. Currently, whiteboard drawings are only captured in recordings but not shared live between participants.Enhancement 7 — Attendance Tracking and AnalyticsImplement actual attendance recording using LiveKit participant_joined and participant_left webhook events. Build a database model for attendance records and serve real analytics data to the teacher's analytics dashboard (replacing the current static data).Enhancement 8 — Mobile-Responsive PWAConvert the VEDU frontend into a Progressive Web App (PWA) with a manifest.json and service worker. This enables Add to Home Screen on Android/iOS devices, offline schedule viewing via service worker caching, and push notifications for class reminders.Enhancement 9 — Assignment Management SystemImplement the currently stubbed 'Assignments' navigation link with a full file upload (MinIO), deadline tracking, and teacher feedback workflow.Enhancement 10 — TURN Server IntegrationFor organizations with strict symmetric NAT or corporate firewalls that block UDP, integrate Coturn TURN server. LiveKit supports TURN configuration in livekit.yaml. This would eliminate connectivity issues for the minority of users whose networks block UDP WebRTC.Enhancement 11 — Kubernetes Deployment (Scalability)Migrate from Docker Compose to Kubernetes (Azure AKS) for horizontal scalability. LiveKit supports multi-node clustering with Redis as the shared state store. This would allow VEDU to scale to hundreds of simultaneous rooms across multiple VMs.Enhancement 12 — Flyway Database MigrationsReplace hibernate.ddl-auto=update with Flyway versioned SQL migration scripts. This provides auditable, incremental schema evolution with rollback capability — essential for production systems with data loss risk.CHAPTER 24: LIMITATIONS AND FURTHER ENHANCEMENTS24.1 Current LimitationsLimitation 1 — JWT Signature Not VerifiedThe TokenService extracts JWT claims by Base64URL-decoding the payload without cryptographically verifying the HMAC-SHA256 signature. A malicious user who constructs a JWT with a fake sub claim can impersonate any user ID for read operations. This is a known security limitation documented in Part VIII.Limitation 2 — Admin Endpoints UnauthenticatedThe /api/admin/* and /api/admin/entities/* controllers perform no authentication checks. These endpoints expose full CRUD operations on all entities and must be protected by network-level controls (firewall, VPN) in production.Limitation 3 — Whiteboard Not Synchronized in Real TimeThe HTML5 canvas whiteboard captures drawings locally. While the whiteboard IS captured in session recordings (LiveKit Egress renders the full DOM), other live participants cannot see whiteboard annotations in real time. Each participant sees only their own local canvas state.Limitation 4 — Single Egress Container (Recording Scale)LiveKit Egress runs as a single container. Each composite recording requires one Chromium browser instance, which consumes approximately 500 MB RAM. The current VM (4 GB RAM) can support at most 3-4 simultaneous recordings before memory pressure causes failures.Limitation 5 — Hardcoded Analytics DataThe teacher analytics dashboard (teacher/analyitics.html) displays hardcoded static data (85%, 90%, 88%, 92%, 88% attendance; 124 active students; 42 hand raises). Real attendance tracking is not implemented.Limitation 6 — LocalDateTime Without TimezoneSchedules are stored as LocalDateTime without timezone information. If teachers and students span different timezones, schedule times will be interpreted relative to each user's browser timezone, potentially causing confusion. ZonedDateTime with UTC storage would be more correct.Limitation 7 — Room Name = Topic NameThe LiveKit room name is directly set to the schedule's topicName. If two teachers create schedules with identical topic names simultaneously, they will share a LiveKit room. A UUID-based room naming approach would prevent this collision.Limitation 8 — No Automated TestsBeyond the scaffolded contextLoads() smoke test, there are no automated unit, integration, or E2E tests. This limits confidence in refactoring and increases regression risk.Limitation 9 — No TURN Server for Restrictive NetworksInstitutions with symmetric NAT or corporate firewalls that block all UDP will experience WebRTC connectivity failures. A Coturn TURN server would provide TCP fallback for media transport in these environments.Limitation 10 — MinIO Anonymous Bucket PolicyRecording files are publicly accessible to anyone who knows the URL. While ListBucket is not anonymous, the URLs themselves are not access-controlled beyond obscurity. Time-limited presigned URLs are the recommended solution.CHAPTER 25: CONCLUSIONVEDU — Virtual Education Platform represents a comprehensive demonstration of modern cloud-native web application development, combining WebRTC real-time communication, microservices containerization, S3 object storage, automated email delivery, and role-based access control into a cohesive, production-deployed educational platform.The project successfully achieved all primary objectives defined in Chapter 2. A browser API and protocol standard enabling peer-to-peer audio, video, and data transfer without plugins. Mandatory encryption via SRTP.SFU (Selective Forwarding Unit):  A WebRTC server that receives encoded streams from each participant and forwards them to subscribers without decoding. LiveKit implements an SFU. More scalable than MCU.ICE (Interactive Connectivity Establishment):  The WebRTC framework for finding the best network path between endpoints using STUN, TURN, and local network candidates.STUN:  Session Traversal Utilities for NAT. Allows a device behind NAT to discover its public IP and port for WebRTC connectivity.SRTP:  Secure Real-Time Transport Protocol. Mandatory encrypted transport for WebRTC audio/video streams. Keys exchanged via DTLS-SRTP during ICE.JWT (JSON Web Token):  A compact signed token (header.payload.signature) for transmitting user identity claims. Supabase signs JWTs with HMAC-SHA256.Spring Boot:  Opinionated Java framework with embedded Tomcat, auto-configuration, and production-ready features. VEDU backend uses version 3.1.2.JPA (Java Persistence API):  Java specification for ORM. Spring Data JPA implements it using Hibernate to translate entity operations to SQL.MinIO:  Self-hostable S3-compatible object storage server. VEDU stores session recordings as MP4 files in MinIO.Egress (LiveKit):  LiveKit's recording service. Uses headless Chromium to render the room, FFmpeg to encode H.264/AAC MP4, and S3 PUT to upload to MinIO.Supabase:  Open-source Firebase alternative. Provides managed PostgreSQL, Auth, and PostgREST. VEDU uses Supabase Auth and PostgreSQL database.PostgREST:  Auto-generated REST API over PostgreSQL. Supabase exposes it at /rest/v1/*. VEDU uses it for profile table reads/writes.Caddy:  Modern web server with automatic HTTPS via Let's Encrypt ACME protocol. Used as VEDU's reverse proxy and TLS terminator.Redis:  In-memory key-value store used by LiveKit for room state management, participant tracking, and pub-sub across server nodes.Docker Compose:  Tool for defining multi-container applications in a YAML file. VEDU uses it to orchestrate 8 containers.Glassmorphism:  UI design style with frosted-glass effects: backdrop-filter:blur(), translucent backgrounds (rgba), and subtle borders on glass-like surfaces.Simulcast:  WebRTC technique where a publisher sends multiple quality encodings simultaneously. SFU forwards appropriate bitrate per subscriber.HMAC-SHA256:  Hash-based Message Authentication Code using SHA-256. Used by Supabase to sign JWT tokens. VEDU should verify this signature in production.RTMP:  Real-Time Messaging Protocol. Streaming protocol used by OBS Studio to send video to servers. LiveKit Ingress accepts RTMP on port 1935.UUID:  Universally Unique Identifier. 128-bit RFC 4122 value formatted as 8-4-4-4-12 hex. Supabase Auth assigns UUIDs to all users.JPQL:  Java Persistence Query Language. Object-oriented query language operating on JPA entities, not tables. Used for custom queries in VEDU repositories.Lombok:  Java compile-time annotation processor generating boilerplate (getters, setters, constructors, toString, equals) — eliminating hundreds of lines of repetitive code.DDL (Data Definition Language):  SQL subset for schema management (CREATE TABLE, ALTER TABLE). Hibernate generates DDL automatically with ddl-auto=update.Presigned URL:  Time-limited signed URL for direct S3/MinIO object access without credentials. Recommended future improvement for VEDU recording security.HLS (HTTP Live Streaming):  Apple's adaptive bitrate streaming protocol segmenting video into .ts chunks served via .m3u8 playlists. Planned as a VEDU future enhancement.CORS (Cross-Origin Resource Sharing):  Browser security mechanism restricting cross-origin HTTP requests. Not triggered in VEDU production (same-origin), but relevant in local development.Bean Validation:  Java EE specification for declarative input validation using annotations like @NotBlank, @Email, @Size. Not yet implemented in VEDU DTOs.APPENDIX F: DATA DICTIONARYThe data dictionary defines all data elements used across VEDU's database tables, DTOs, and API payloads — including type, constraints, defaults, and business rules.F.1 Student EntityAttributeDB ColumnTypeNullDefaultBusiness RuleididUUID varchar(36)NO—Set from Supabase Auth UUID.
